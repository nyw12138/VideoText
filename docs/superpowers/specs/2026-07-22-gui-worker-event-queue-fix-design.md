# VideoText GUI 工作进程消息修复设计

## 背景与根因

GUI 启动工作进程后，控制器使用后台线程读取标准输出，但回调会在该后台线程中直接调用 `Tk.after()`。Tkinter 界面操作必须由创建 Tcl/Tk 解释器的主线程执行；跨线程调度一旦阻塞或抛出异常，读取线程就无法继续消费消息、等待进程退出、清理临时目录或恢复界面状态。

现场证据表明任务目录已经产生 `downloaded.m4a` 和 `normalized.wav`，证明下载及标准化确实执行过；与此同时界面仍显示“就绪”、阶段为空，说明故障位于后台进度消息到 GUI 的交付边界，而不是网址解析。

## 修复目标

- 后台线程不调用任何 Tkinter API。
- 界面按顺序显示启动、读取信息、下载、标准化、GPU 转写、导出和完成状态。
- 工作进程退出或消息处理异常时，界面总能恢复为可再次启动的状态。
- GPU 转写较慢时保留当前阶段和持续计时，让用户能够区分“正在工作”和“界面失联”。
- 诊断信息写入日志并可从界面复制。
- 不修改下载器、Whisper 模型、CUDA 配置和输出文件格式。

## 设计

### 主线程事件队列

`VideoTextApp` 持有一个线程安全 FIFO 队列。传给 `WorkerProcess.start()` 的消息回调和退出回调只向队列写入普通 Python 数据，不访问 `root` 或任何控件。

GUI 主线程通过启动时注册的周期性 `root.after()` 轮询队列，并在主线程中调用 `handle_message()` 和 `handle_exit()`。来自同一读取线程的终止事件排在所有输出消息之后，因此完成或错误消息会先于退出处理。

### 状态与故障处理

点击“开始转换”后立即把状态设为“正在启动工作进程”。收到 `started` 后显示“工作进程已启动”，收到 `progress` 后更新当前阶段。转写阶段没有新增消息时，状态继续保持“正在使用 GPU 转写”，计时继续增加。

主线程处理事件时捕获意外异常，记录完整堆栈并恢复按钮状态；控制器的读取线程也使用 `try/finally` 确保等待进程、读取标准错误、清理本次任务临时目录并发送退出事件。退出详情进入旋转日志和“复制详细信息”。

### 生命周期

事件轮询只由 GUI 主线程调度。窗口关闭且没有任务时正常保存设置并销毁；有任务时沿用现有取消机制，收到对应退出事件后再销毁。过期任务事件不得改变新任务状态。

## 测试与验收

- 单元测试证明工作线程回调只入队，不触发 Tkinter。
- 单元测试证明队列按消息、终止事件的顺序由主线程消费。
- 覆盖 `started`、正常完成、业务错误、原生崩溃和事件处理异常。
- 运行完整 `pytest`、Ruff 和 `compileall` 回归检查。
- 使用用户提供的 Bilibili 地址进行一次实际 GUI 转写，确认阶段显示、结果输出及任务结束后的按钮状态。
